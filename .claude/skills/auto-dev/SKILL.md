自律開発の1サイクルを実行する。憲法は docs/VISION.md、評価基準は docs/CRITERIA.md。

## 手順

1. **文脈の読込**: docs/VISION.md → docs/CRITERIA.md → **docs/WRITING.md（コンテンツタスクのとき。執筆規律）** → docs/JOURNAL.md（**live のみ**。末尾の申し送り。`JOURNAL-archive.md` は読まない）→ docs/BACKLOG.md（**live のみ**。`BACKLOG-done.md` は読まない）の順に読む。安定ファイル（VISION/CRITERIA/WRITING）を先に読むとサイクル間のプロンプトキャッシュに乗りやすい。
2. **タスク選択**: BACKLOG の上から、着手可能な最初のタスクを1つ選ぶ。**⛔**（＝ハード境界。定義は CLAUDE.md）の印があるものは飛ばし（下ごしらえ・改訂案の提案は可）、次の着手可能タスクへ進む。**eval-work の 3点未満が残っている作品の続章執筆タスクは着手不可**（その修正が先）。「体験の漂流」診断は着手不可にせず、次章に織り込む宿題として扱う。「AI が進めてよいか？」の類いは人間の返事を待たず自律に判断して進める。着手可能なタスクが本当に無いときだけ、その旨と「人間に決めてほしいこと」を **docs/REVIEW.md に集約して**終了する（step 9）。
3. **作業場所**: **main で直接作業する**（feature ブランチは作らない——人間の指示）。commit は main に直接行い、公開（push）は人間に委ねる。
4. **実装**: CLAUDE.md の規約に従って実装する。コンテンツは「章1つ」「シーン1〜2個」など、1セッションで品質を保てる粒度に刻む。タスクが大きすぎたら BACKLOG 上で分割し、先頭の断片だけやる。
5. **検証**:
   - コード: `npm run check` と `npm test`。ビルドに関わる変更なら `npm run verify`。
   - ビジュアル（`src/engine/art/`・`src/engine/map/`・faces.ts の変更時、**および map.ts のシーン地図・story の closeup/figure データの新規執筆・変更時**）: `/visual-check` で目視確認（破綻チェック＋初見読解 self-check）。
   - 作品データ（本文・カード・手がかり等）を変えたら: `/eval-work` で多角評価。G に落ちたら直す。**再評価は影響軸だけ・最大2ラウンド**（eval-work step5＝トークン規律）、直らなければコミットせず報告する。
6. **自己レビュー（ロジック差分のときだけ）**: 差分がエンジン/ロジック（`src/engine/**`・`.svelte`/`.ts` の振る舞い）を含むときだけ、**code-reviewer サブエージェント（sonnet, effort low）**に差分を渡し確度の高い指摘だけ返させて直す（本流でインライン実行しない＝差分を本流に載せない）。純コンテンツ変更（`story/**`・データ・本文・docs）は step 5 で足りるのでスキップ。
7. **コミット**: 英語1行メッセージで main にコミット（規約どおり）。**push はしない**（人間が行う）。
8. **記録＋掃き出し（毎サイクル）**: BACKLOG を更新し、JOURNAL **live** 末尾にセッション記録（日付・タスク・評価要点・**AI→AI の申し送り**）を追記する。**人間宛の個別お願いは REVIEW.md へ**（step 9）。**live を痩せて保つのは完了時でなく毎サイクルの掃き出し**（無人ループでは溜めると誰も掃除しない）:
   - 完了タスクは `[x]` にした同サイクルで詳細を docs/BACKLOG-done.md へ移し、live は1行スタブ＋commit 参照だけにする。
   - 「未整理」は append 専用にしない——park した監視・微磨き followup は逐語を残さず要点1行＋git／JOURNAL-archive 参照に畳む。新規 followup は次サイクルの着手項目に限る。
   - JOURNAL live は docs-budget のバイト予算で self-prune（件数でなくバイトが基準）＝上限に近づいたら最古の全文エントリを docs/JOURNAL-archive.md へ移し1行スタブに畳む。スタブ塊が太ったら古い群をグループ・スタブへ集約する（本文＝学びは archive／git）。
   - **機械ゲート**: `tests/docs-budget.test.ts` が BACKLOG/JOURNAL のバイト上限を step 5 の `npm test` で強制。赤なら掃き出してから commit する（上限を上げて回避しない。下げる方向は自律で可）。
   - まとめて main にコミットする。
9. **人間面の最新化（毎サイクル・唯一の人間宛出力）**: docs/REVIEW.md を**上書き集約**する（追記でなく最新化。節構成は REVIEW.md 自身が定義＝人間が週1で読む唯一の1枚。`tests/review-shape.test.ts` が形を守る）。人間宛の事項はここへ畳み JOURNAL/BACKLOG に散らさない。任意の実機目視・UX 磨きは毎サイクル人間に宛てず、SVG 自己点検で担保できる分は担保して残りをバッチに束ねる。attended run（対話中）のときだけ会話出力で口頭報告してよい。

## コンテンツ工程（教科書化ドリフト防止）

執筆規律は **docs/WRITING.md**（書法・体験予算・章カルテの装置欄・パイロットシーン制）。このループが毎サイクル足す手順は2つだけ:

- **累積離脱テスト**: 新しい章をコミットするサイクルでは、差分評価に加えて「**章1から通しで読む離脱テスト**」を1本走らせる（sonnet 1本・軽量。どの章のどこで読むのをやめるか）。個々の差分が pass でも作品全体が漂流する事故を捕まえる。
- **作りだめより実測を優先**: 観察を経ていない執筆済み章が2章以上あるとき、章執筆と非章タスクが両方着手可能なら非章タスクを先に採る。**優先順位であって停止ではない**。

## トークン規律（無人ループ前提）

`claude -p "/auto-dev"` を無人で反復する前提で、品質を保ったままトークンを抑える技法。

- **モデル/努力度はフェーズ別に。** 質が要るのは本文執筆（craft）で、推論難度は高くない。
  - メインループ（統括＋本文執筆）の既定努力度は**起動側の設定**で決まる（スキルからは変えられない）。`xhigh` でなく `high` を推奨——物語・ふりがなの質はほぼ不変で思考トークンが大きく減る。
  - **重い下請けは fork でなく「新規サブエージェント」に安価モデルで出す**（fork はメインの全文脈を継承するので種付けコストが同じ。サブエージェントのツール出力＝ファイルダンプ/テストログ/SVG は本流の文脈に残らない）:
    - 探索・grep・「どこにあるか」 → **Explore（sonnet）**。ファイルダンプを本流に載せない。
    - `/eval-work` の並列エージェント（3ペルソナ＋VISION監査）→ **sonnet / effort medium**。ファクトチェックの**反証ステップだけ opus / high**（誤採用の防止線）。
    - 自己レビュー（step 6）はコスト最大費目——インラインで差分を読むと文脈が 150k 超に膨らむので、ロジック差分時のみサブエージェント経由に絞る。
    - テスト/verify のログが膨らむ時 → サブエージェントで走らせ **pass/fail＋該当行だけ**返させる。
    - 記帳（BACKLOG/JOURNAL/commit の機械作業）→ **haiku/sonnet**。
- **可変ファイルを小さく保つ。** JOURNAL/BACKLOG は毎サイクル書き換わりキャッシュを busts する＝バイト数がそのまま毎サイクルの再処理トークンになる。step 8 の掃き出しで live を小さく保ち、安定ファイルを先に読む（step 1）ことでミス幅を抑える。上限は `tests/docs-budget.test.ts` が毎サイクル強制（step 8 の機械ゲート）。
- **検証は最小十分から段階的に。** 通常は `npm run check` ＋ 対象作品の `npm test -- <file>`。`npm run verify`（全インライン build）は build 影響変更のときだけ。
- **無人での visual-check。** 人間確認（SendUserFile）は無人ループでは応答が返らない。art/map/closeup/figure を触ったら **SVG をテキストとして読む自己点検を主**とし、ラスタ（vision）読み込みは自己点検で判断がつかない時と**新規執筆の主ビジュアルの初見読解チェック**（伝わるかは座標の数値では判定できない）に絞る（vision トークンは高い）。SVG 自己点検で担保しきれない大規模な描画改修は、無人ループでは着手せず attended run 向けに BACKLOG へ回す判断もある。

## ガードレール

**運用規則（単一ゲート原則・ハード境界3つ・main 直接作業・push しない・停止条件の作り方）は CLAUDE.md「自律開発」節が唯一の真実**——ここには再掲しない。このループ固有の作法だけ:

- 1サイクル1タスク。終わったら止まる（連続実行は人間が /loop 等で明示的に指示したときのみ）。
- 判断に迷ったら（ハード境界以外）、**安全側に倒しつつ自律に決めて進める**。迷いの理由と採った判断は JOURNAL / BACKLOG に残す。
