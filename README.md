# rekishi-play — 歴史人物「なりきり」インタラクティブ教材

### ▶ 遊ぶ: **https://hidai.github.io/rekishi-play/**

インストール不要・ブラウザだけで動きます（アカウント登録なし。進みぐあいはその端末のブラウザに保存されます）。

10〜14歳の子どもが、歴史上の人物ひとりの一生を「なりきって」遊ぶ、インタラクティブな日本史（＋世界史予定）作品集です。人物を英雄にも悪役にもせず、迷い・矛盾・弱さ・したたかさを含む「人間まるごと」に触れさせる——大目標と設計原則は [docs/VISION.md](./docs/VISION.md)（このプロジェクトの憲法）にあります。

## 遊び方

1. https://hidai.github.io/rekishi-play/ を開く。
2. 「**だれで あそぶ？**」で名前を作る（ふりがな ON/OFF・昼夜もこの名前について回る。きょうだいで枠を分けられます）。
3. 「**なりきる 人を えらぶ**」で作品を選ぶ（各作品の下にその子の進みぐあい。画面下の「時代の ものさし」で主人公6人が1本の西暦の線に並びます）。
4. 第1章から順に、**その人物本人になって人生の岐路で選択**していきます。
5. 選んだ後に「**史実では…**」パネルが開き、自分の判断と歴史のギャップから「なぜ？」が生まれます。
6. 章をクリアすると「手帳」に、ことばカード・人物カード・手がかり・「えっ！？」がたまります。

## 全作品共通の装置（エンジン）

[docs/VISION.md](./docs/VISION.md) の設計原則を、エンジンが作品非依存の装置として実装しています。新作品は作品データ（`Work` 型）を書くだけで、これらが全部ついてきます。

| 原則 | エンジンの装置 |
|---|---|
| 外れ＝学びの入口 | どれを選んでも死なずに進み、非史実の選択には「もしもルート」（反実仮想を見せてから史実に合流）。選択肢の表示順は毎回シャッフル（`engine/order.ts`）。章クリアで「きみの読み」（史実一致数、`engine/canon.ts`）。「分かれ道図鑑」（`engine/branches.ts`）に選んだ枝の結末がたまり、えらばなかった枝は「えらぶと ひらく」＝再プレイの動機。 |
| 貫通する謎 | 第1章で提示 → 章ごとに手がかりが1つずつ → 終章で子ども自身の答えを出す。 |
| 収集と再訪 | ことばカード・人物カード・手がかり・「えっ！？図鑑」（`engine/sparks.ts`）・信条（`engine/creeds.ts`）・年表・進軍の地図。クイズ（`engine/quiz.ts`）は顔あて/信条→章あて/関係あてで人物像を能動的に想起させる。作品をまたいで**同じ人**が出る場合は、人物カードに相手の作品での説明が並ぶ（`works/bridges.ts` ＋ `engine/crosswork.svelte.ts`）——未プレイなら誘い一行だけで中身は見せない。 |
| 人物は「声」と「信条」で刻む | 鍵人物にひと言の台詞（`.speak`。敵にも声を与える）、主人公には章の山場ごとに一人称の決め台詞＋象徴アクション（`Scene.creed`）。 |
| 体感 > 情報 | 効果音（Web Audio でその場合成＝音源アセット無し、`engine/sfx.svelte.ts`）・選択でメーターが弾む手ざわり・人生ステージの見せ場・一度きりの全画面 reveal・「対面の場」（感情が主語のシーンで地図の代わりに人物のバストアップ、`engine/art/closeup.ts`）・段取りミニゲーム（`engine/minigame.ts`）。 |
| わからないことは宝 | 「実はよくわかっていない！」（spark）を章クリアで収集。本文の「たしかさマーク」◎○△☆が確度の4段階を示す。 |
| ふたつの学年にひとつの本文 | ルビつき1系統の本文＋ふりがな ON/OFF スイッチ。深さは「🔍 もっと深く」パネルに格納し、学年でなく好奇心で扉が開く。 |

作品どうしは「**時代の ものさし**」（`engine/chrono.ts`）でも並びます——作品えらび画面と手帳の年表タブの上に、主人公全員の生没年を1本の西暦軸に置いた帯が出て（帯の長さ＝生きた年数、「ごろ」の側は端をぼかす）、「清盛と政子は同じころ」「ダ・ヴィンチは秀長より前」が説明なしで見えます。時代名（平安・鎌倉…）は海外の人物が同じ線に並ぶためあえて書きません。

物語のメイン画面は原則、シーンごとの「**読み解き地図**」（`engine/map/`）——本文に出る地名・人物・できごとを実地理の上に重ね、シーンの範囲へ自動ズームし、隅の全国ロケーターで「日本のどこか」を常に示します。似顔絵はかぶりもの・ひげ・表情・虹彩色などをパラメータで描き分ける学習まんが調のジェネレータ（作品側 `faces.ts` ＋ エンジン側 `faceArt`）で、地図上の顔はタップで人物カードが開きます。

### 実例（第1作・秀長）

設計原則を人物に合わせて具体化した初出の実例（VISION「設計原則」の参照先）:

- **貫通する謎**: 「なぜ天下人の実弟なのに教科書に載らないのか」。負の定義（記録に残らない裏方）に対し、信条（「兄が攻める。おれは動かない。」等）で正の定義を対で立てる。
- **段取りミニゲーム**: 主役の核＝「段取り」を手で組み上げて体感する（墨俣一夜城・中国大返し・郡山の町づくり の3面）。
- **対面の場**: 母の見送り・信長の値踏み・利休の茶室・兄の見舞い——「だれ・想い」が主語のシーンは地図でなく人物の顔を大きく見せる。
- **兄弟の別れ**: 終章「最後に、兄へ何と言う？」——「ふたりの最後のことばは、記録にない。だから、いまきみが言ったそれが、ふたりの最後のことばだ」。"記録に残らない"という主題を、子ども自身の選択で埋めさせる。

## 技術メモ

- **配信の形**: 要件は2つだけ——**配信先の base path に依存しない**（GitHub Pages のサブパス、将来の独自ドメイン直下のどちらでも動く）と、**外部リソース読込ゼロ**（ランタイム外部依存ゼロ）。`tests/deploy-contract.test.ts` がこの2点を検査する。実装は `base: './'` の**チャンク分割ビルド**（`dist/index.html` ＋ `dist/assets/*`）。かつては `vite-plugin-singlefile` で1ファイルに畳んでいたが、カードに実物の写真（`Card.photo`＝PD の複製を data URI で同梱）が入って全作品ぶんを毎回運ぶ形になったため分割へ移した——入口（`src/works/registry.ts`）が既に「一覧は軽量 card・本体は `load()` で遅延」の契約なので、**秀長の写真は秀長を開いたときだけ届く**。ブラウザの `prompt`/`confirm`/`alert` は使わず自前ダイアログ UI（`engine/dialog.svelte.ts`）。
- **エンジンと作品の分離**: 両者の契約は `Work` 型（`src/engine/types.ts`）。エンジンは作品固有の定数（章数・主人公 ID 等）を持たない。
- **ビジュアルは全てインライン SVG**＋絵文字＋CSS アニメーション。似顔絵は `<defs>`・`id` を含まない純粋 SVG（複数の顔が同一 DOM に同居するため）。地図は緯度経度の地名辞書（gaz）を実行時投影（`engine/map/project.ts`）で SVG 座標化する。
- **地図データ出典**: [dataofjapan/land](https://github.com/dataofjapan/land)（国土数値情報 由来の都道府県境界 GeoJSON）を簡略化して inline。海外海岸線は Natural Earth 系データから同様に生成。
- **進捗の保存**: localStorage キー `rekishi_play_account_v1` の**1つ**に保存。「だれで あそぶ？」で選ぶアカウントが作品を横断し（名前・ふりがな・昼夜は共通）、進みぐあいは作品ごとの枠（`Account.works[work.id]`）に分かれる。端末をまたぐ引き継ぎは非対応。

## 開発

```bash
npm install
npm run dev       # 開発サーバ（HMR）
npm run check     # svelte-check（型・a11y）
npm test          # vitest（セーブ互換・作品整合・体験予算・ビジュアル回帰 ほか）
npm run build     # dist/ を出力（index.html ＋ assets/ のチャンク）
npm run verify    # build → 全テスト
```

ビジュアルの目視確認ツール（描画の破綻も「初見の子どもに伝わらない絵」も型チェックでは検知できないため）:

```bash
npx vite-node scripts/render-faces.ts <出力ディレクトリ>        # 全人物の似顔絵コンタクトシート
npx vite-node scripts/render-scene.ts <出力.svg> [章] [シーンid] # シーンのメインビジュアル
npx vite-node scripts/visual-coverage.ts [作品slug]             # 全シーンの主ビジュアル在庫レポート
```

## 作品を追加する

作品追加は基本的に「フォルダ追加 ＋ 登録先2つに1件ずつ」:

1. `src/works/<新作品>/` を作り、`meta.ts` / `cards.ts` / `clues.ts` / `timeline.ts` / `story/` / `map.ts` / `faces.ts` を用意（既存作品が雛形。`meters.ts` / `relations.ts` / `photos.ts` / `figures.ts` は必要な作品だけ）。
2. `index.ts` で各データを `Work` 型に束ねて export。
3. `src/works/registry.ts` の `WORK_ENTRIES` に1件（アプリの入口＝軽量な `card` ＋ 本体を遅延 import する `load()`）。
4. `src/works/index.ts` の `WORKS` に1件（開発ツール・テストゲート用の同期版）。3と4のズレは `tests/work-registry.test.ts` が落とします。
5. 既存作品と同じ人物が出るなら `src/works/bridges.ts` に1行（作品どうしを名寄せする表。ここに無い id の重複は `tests/cross-work.test.ts` が落とします）。

エンジン側の変更は不要です（登録が1作だけのビルドでは作品選択画面を自動でスキップします）。作品データは信頼済み HTML として `{@html}` で描画されるため、実行時の外部入力を混ぜない静的な手書きデータに限ります（詳細は `src/engine/types.ts` の `Work` 型ヘッダ）。

## 開発体制（AI 自律開発）

このリポジトリは AI（Claude Code）による自律開発を前提に運用しています。判断の拠り所は `docs/` に集約:

- [VISION.md](./docs/VISION.md) — 憲法（大目標・設計原則・アンチゴール）。改訂は人間のみ
- [CRITERIA.md](./docs/CRITERIA.md) — マージ可否の評価ルーブリック
- [WRITING.md](./docs/WRITING.md) — 執筆規律（シーンの書法と体験予算）
- BACKLOG.md / JOURNAL.md / REVIEW.md — タスク待ち行列・AI 間の申し送り・人間が週1で読むレビュー面（済んだ分は `BACKLOG-done.md` / `JOURNAL-archive.md` へ掃き出す。live 面のサイズは `tests/docs-budget.test.ts` が上限を守る）

運用規則（単一ゲート原則・ハード境界）は [CLAUDE.md](./CLAUDE.md)。最終評価者は子どもたちのプレイ観察（BACKLOG の観察メモ）がすべての AI 採点に優先します。

## デプロイ

main ブランチへの push で GitHub Actions（[`.github/workflows/deploy.yml`](./.github/workflows/deploy.yml)）が `npm run build` を実行し、生成した `dist/` を GitHub Pages（https://hidai.github.io/rekishi-play/ ）に公開します。配信 URL は固定なので localStorage のセーブが引き継がれます（独自ドメインへ移す場合はセーブが引き継がれない点に注意——localStorage は origin ごと）。
